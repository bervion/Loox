## 2. Gaps, ranked by user impact

**GAP-1 (High) — `disabledByUser` does not hide surfaces.** Product wants: setting off ⇒ hidden entirely. Today only the item editor honors that.
- `ShareAccessSheet.swift:462-481` — "Quick Link" chooser row always visible; tapping it lands on a form whose only create path says "Share Links are turned off in Settings." (`QuickLinkView.swift:219`). Expected: hide the chooser row (fall straight to the Loox-user flow) when `availability(.shareLink, .create) == .disabledByUser`. Minimal fix: one `if` around the `shareOptionRow` mirroring `ItemEditorScreen.swift:529-531`.
- `LooxHubScreen.swift:143-156` — "Private Email" / "Share Links" tiles always visible. Expected: hide (or grey with "Off" metric) when the pref is off. Minimal fix: gate each tile on `env.capabilities.userPreference(id)`.
- Note: local records must STAY visible everywhere (INV-CAP-05/10) — hiding applies to create-entry surfaces only.

**GAP-2 (High) — silent dead-tap on Private Email create when pref is off.** With `disabledByUser`: `CapabilityBannerView` deliberately renders nothing (`CapabilityBannerView.swift:52-53`), yet "Create reusable address" / "Add site-specific address" stay visible (`PersonaAliasesScreen.swift:151-155,173-174`) and `guardEmail` returns silently (`:241-245`). The user taps and nothing happens, with no explanation anywhere on screen. Same silent-return also fires for offline/maintenance (banner explains it above, but the tap itself is still a no-op with no feedback). Expected: hide the create rows when `.disabledByUser` (product rule), and for other blocked states either disable the rows visually or scroll to/flash the banner. Minimal fix: wrap the two create buttons in `if createState == .available` (records and delivery sections untouched).

**GAP-3 (Medium-High) — Erase Vault: wrong copy for non-offline failures; retired relay bricks erase.** `eraseWithRelayTeardown` catches every `RelayService.Failure` as `relayBlockErase` (`SettingsScreen.swift:41-52`) and the alert always says "Network needed … Connect to the internet" (`:217-221`). During a relay outage/maintenance the user is online and the copy is wrong; if privateEmail is ever `retired`, `send()` throws `capabilityBlocked(.retired)` forever (`RelayService.swift:277-341`) and Erase Vault becomes permanently impossible. Expected: per-state copy (reuse `Failure.userMessage`, `RelayRetryPolicy.swift:45-80`), and a policy decision for retired (retired ⇒ backend already tombstoned forwarding ⇒ erase should proceed). Minimal fix: catch `capabilityBlocked(.retired)` → proceed with erase; otherwise surface `failure.userMessage` instead of the fixed string.

**GAP-4 (Medium) — Quick Link create/revoke failures show raw transport text, and revoke failure nukes the form.** `QuickLinkView.create/revoke` render `error.localizedDescription` (`QuickLinkView.swift:246,253-256`). Capability errors carry good copy (`LooxLinkAPIClient.swift:15-26`), but a mid-create connection drop shows NSURLError system text ("The request timed out.") instead of the capability offline/outage vocabulary, and a failed swipe-revoke replaces the entire config form (field pickers, history) with the full-screen `.failed` state. Expected: map `URLError`/5xx to the same footnote copy used at render (`shareStateFootnote`, `:212-223`); keep revoke failures as an inline alert like `PersonaAliasesScreen.swift:105-108`. Minimal fix: a small error-mapping helper + an `@State` alert for revoke.

**GAP-5 (Medium) — no screen-open health probe for shareLink/quickView ⇒ stale availability.** Only `PersonaAliasesScreen` probes (`:87,228-236`); `CapabilityHealthProbe` supports all four IDs (`CapabilityHealthProbe.swift:12-24`) but is never called for `.shareLink`/`.shortLink`/`.quickView`. Consequences: `QuickLinkView` renders "available" during an un-observed worker maintenance until a create fails (`QuickLinkView.swift:163`); the Settings "Khả dụng" subtitle (`SettingsScreen.swift:29-31`) reflects only persisted mode + connectivity, never current health. Expected: fire the non-blocking probe on QuickLinkView appear and (throttled) on the Settings screen — exactly the pattern at `PersonaAliasesScreen.swift:86-87`. This is also the prerequisite for an honest status-dot row (§4).

**GAP-6 (Medium) — Loox Link App Attest traffic bypasses breaker admission.** In `createLink` the App Attest challenge/assertion round-trip (`LooxLinkService.swift:64-76`, network via the same worker) runs BEFORE `allowRequest(.shareLink)` (`:78-80`); `shorten` has the same order (`:144-161`). During a confirmed outage the app still fires unguarded attest requests (and burns single-use challenges). `RelayService.send` shows the correct order — breaker first (`RelayService.swift:277-280`). Minimal fix: hoist the `allowRequest` guard above the attestation block in both functions.

**GAP-7 (Low-Medium) — passcode-unlock cold session never triggers the control-plane refresher.** `refreshIfNeeded(.launchAfterUnlock/.foreground)` fires only from `handleScenePhase(.active)` when already unlocked (`App/RootView.swift:94-107`); the unlock `onChange` runs reload/sync only (`:55-61`). Face ID unlocks cycle `.inactive→.active` so they refresh, but a passcode unlock keeps the scene `.active` throughout — the manifest/registry/keyset can stay unfetched for the whole session (violates INV-CP-01/04 in that path; fails SAFE for quickView, which just stays hidden, `QuickViewExposureProvider.swift:40-48`). Minimal fix: also spawn the refresher task from the unlock `onChange` (it self-dedupes, `SignedControlPlaneRefresher.swift:63-66`).

**GAP-8 (Low) — extension capability snapshot is write-only.** `CapabilityStore.setMode` writes the App Group snapshot for the extension (INV-CAP-06, `CapabilityStore.swift:134-137`), but `CapabilitySnapshot.read` (`VaultifyCore/Models/CapabilitySnapshot.swift:33`) has zero callers outside tests; `VaultifyAutoFill/` contains no `Capability`/`URLSession` reference at all. No user impact today (the extension has no capability surface) — either wire it when the extension grows one, or note it as dormant.

Non-gaps verified (documented so they aren't re-flagged): shorten failure copy is honest degrade (`QuickLinkResultView.swift:112-119`); shared-item gate offline behavior is exemplary (`SharedAccessGateView.swift:33-49`); Watchtower fail-soft + "incomplete online checks" footnotes (`AuditCoordinator.swift:52-68`, `VaultAuditFlowScreen.swift:195-200`); breaker/backoff bounded everywhere (all clients set explicit timeouts: 10-30 s, e.g. `LooxLinkAPIClient.swift:185`, `QuickViewAPIClient.swift:163`); `ShareAccessSheet` waiting poll is bounded and says so (`ShareAccessSheet.swift:349-383`).

## 3. Offline-first / INV-CAP-02 verification — HOLDS

- **Startup:** `AppEnvironment.init` performs no network: capability/manifest/registry/keyset are `applyCached()` local-only (`App/AppEnvironment.swift:246-251`); `entitlements.start()` is a local StoreKit listener (`:261-263`). Control-plane refresh runs only post-unlock, fire-and-forget (`RootView.swift:101-106`; `SignedControlPlaneRefresher.swift:5-14` "always a detached Task … never awaited on the unlock/render path").
- **Unlock:** Argon2 KDF + local store; the unlock `onChange` triggers `reload()` + `syncNow()` where `syncNow` is `Task { await runSync() }` — non-blocking (`Services/Sync/SyncCoordinator.swift:58-62`).
- **Item CRUD / search:** pure `VaultRepository`/`VaultStore`, no capability consult (INV-CAP-01; resolver short-circuits `read` at `Capability.swift:84`).
- **AutoFill:** extension has zero network and zero capability references (grep of `VaultifyAutoFill/` — no `URLSession`/`URLRequest`/`Capability` hits), matching chaos rows 20-22.
- **Watchtower local audit:** local rules complete regardless of network; the HIBP rule is opt-in and fail-soft (`AuditRunController.swift:39-40`, `AuditCoordinator.swift:52-68`).
- **Sync errors are never modal:** the only surfaces are the Settings status row (`SyncSettingsView.swift:165-177`).
- Only launch-adjacent network found: entitlement attach on a verified StoreKit transaction update (`AppEnvironment.swift:274-276`) — fire-and-forget, not capability, cannot block render.
- Watch item: manifest secondary fetch goes through CloudKit public DB (`CapabilityManifestClient.swift:100-107`) — still only from the refresher/backoff path, never startup.
