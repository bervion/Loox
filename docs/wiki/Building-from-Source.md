# Building from Source

Loox is a SwiftUI app whose Xcode project is generated by [Tuist](https://tuist.dev) from `Project.swift`. The generated `Vaultify.xcodeproj` and `Vaultify.xcworkspace` are gitignored, so every machine generates its own.

## Requirements

- macOS with **Xcode 26.5 or later**. The CI minimum is pinned in `scripts/ci/toolchain-pin.sh` (`MINIMUM_XCODE_VERSION="26.5"`, iOS simulator runtime 26.5 or later).
- [mise](https://mise.jdx.dev), which installs the Tuist version pinned in `.mise.toml` (currently `4.200.1`).
- Deployment targets: iOS / iPadOS 17.3, macOS 15.

## Generate and run

```bash
git clone https://github.com/bervion/Loox.git
cd Loox
mise install
mise exec -- tuist generate
```

Tuist opens `Vaultify.xcworkspace`. Pick the **Vaultify** scheme and run it on an iOS Simulator; no signing is needed there. The Mac app is the same scheme with a My Mac destination.

Regenerate the project whenever you add, remove or rename a source file or edit `Project.swift`:

```bash
mise exec -- tuist generate      # or: mise exec -- make gen
```

Sources are globbed (`Vaultify/**`, `VaultifyCore/**`, `VaultifyAutoFill/**`, `VaultifySafari/**/*.swift`), so a new file does not exist to Xcode until you regenerate.

## Checks

```bash
mise exec -- make check                             # compile the app and embedded extensions for the simulator
mise exec -- make test TEST_TARGETS=VaultifyTests   # unit tests on a throwaway simulator, the suite CI runs
mise exec -- make test                              # unit, snapshot and UI suites
```

`make test` creates one fresh simulator per test target (the suites share a bundle id, so a unit test that writes UserDefaults must not leak into the UI tests), runs the target through `scripts/ci/run-xcode-suite.sh`, prints the pass/fail summary and deletes the simulator. CI (`.github/workflows/ci.yml`) runs the same `VaultifyTests` target on every push to `main` and every pull request, after `scripts/ci/check-privacy-manifests.sh` verifies the required-reason API declarations of the app and the three extensions.

Schemes generated from `Project.swift`:

| Scheme | Purpose |
|---|---|
| `Vaultify` | The app. `make check` compiles this. |
| `Vaultify-UnitTests` | `VaultifyTests` only (XCTest and Swift Testing), what CI runs. |
| `Vaultify-Quality` | `VaultifyTests`, `VaultifySnapshotTests` and `VaultifyUITests`. |
| `Vaultify-StoreKit` | The app with the local `Loox.storekit` configuration so subscriptions can be exercised in the simulator. |

## Generated project rules

- `Project.swift` is the single source of truth for targets, build settings, Info.plist keys, entitlements and the version (`MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`). Edit it, then regenerate. Never edit or commit `*.xcodeproj`, `*.xcworkspace` or `Derived/`.
- The project builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`; crypto and data types are marked `nonisolated` so Argon2 runs off the main thread.
- Argon2 is compiled from the vendored C sources through a bridging header and `HEADER_SEARCH_PATHS = $(SRCROOT)/VaultifyCore/CArgon2`.
- CloudKit code compiles behind the `VAULTIFY_ICLOUD` compilation condition, which `Project.swift` sets for the app and the AutoFill targets.
- A `GoogleService-Info.plist` in `Vaultify/Resources/` configures Firebase. A fork can delete it or replace it with its own: without it the build still succeeds and analytics and crash reporting stay dark.
- `Project.swift` reads two optional environment variables at generation time: `TUIST_LOOX_LINK_PROD_TOKEN` (an anti-abuse token for the Quick Link service, empty on dev machines) and `TUIST_APP_ATTEST_DEBUG_ENVIRONMENT` (`development` or `production`, for Debug builds only).

## Running on a device with your own team and bundle IDs

Simulator runs need nothing. A device run needs a signing team, and several capabilities are tied to the bundle identifiers, so a fork has to rename them consistently:

1. In `Project.swift`, set `DEVELOPMENT_TEAM` to your team and change the bundle IDs of the app (`com.bervion.vaultify`), the iOS and macOS AutoFill extensions (`com.bervion.vaultify.autofill`), the Safari extension (`com.bervion.vaultify.safari`) and the test targets.
2. Update the entitlements files (`Vaultify/Vaultify.entitlements`, `Vaultify/Vaultify-macOS.entitlements`, `VaultifyAutoFill/VaultifyAutoFill.entitlements`, `VaultifyAutoFillMac/VaultifyAutoFillMac.entitlements`, `VaultifySafari/VaultifySafari.entitlements`): the App Group (`group.com.bervion.vaultify`), the keychain access group (`…com.bervion.vaultify.shared`), the iCloud container (`iCloud.com.bervion.vaultify`) and the associated domain for invite links.
3. Update `VaultifyCore/SharedConfig.swift`, which hard-codes the App Group, the keychain access group and the team prefix used by the app and every extension to find the vault file and the biometric key.
4. Register the App IDs in the Apple Developer portal with App Groups, Keychain Sharing and AutoFill Credential Provider (the Safari extension needs App Groups and Keychain Sharing only), plus iCloud/CloudKit and App Attest on the app if you keep those features. Without the App Attest entitlement granted by your provisioning profile, Quick Link, Quick View and Private Email fail on device.
5. Regenerate with `mise exec -- tuist generate` and sign in Xcode.

Forks must ship under their own name and branding: the Loox name, logo and app icon, the Font Awesome Pro `dt_*` and `fa_*` icon assets and the Shopify Polaris icons are not covered by the GPL.

## Release pipeline (for maintainers)

Tags matching `v*` trigger `.github/workflows/release-ios.yml`, which requires a green unit run for the exact tagged commit, regenerates the project, signs with fastlane match and uploads to TestFlight with an App Store Connect API key. `make release`, `make beta` and `make hotfix` bump the version in `Project.swift`, write release notes and create the tag. The full runbook is [docs/deployment-guide.md](https://github.com/bervion/Loox/blob/main/docs/deployment-guide.md).
